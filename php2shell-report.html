왜 그렇게 오래 남아 있었나?

PHP Foundation은 기존 확장 모듈과의 호환성, 성능과 부작용 우려, 합의 중심의 결정 방식, 인력 부족을 함께 지목했다. 따라서 이 사건은 AI의 분석 능력뿐 아니라, 발견한 결함을 실제로 수정·배포할 수 있는 유지보수 체계의 문제이기도 하다.[05]

03 / THE TECHNICAL CORE

같은 뿌리, 다른 실패 지점

메모리를 할당하고 해제하는 순서와, 그 메모리를 가리키는 내부 상태의 수명이 어긋난다.

03
CVE-2026-1096189.2 CRITICAL

초기화 도중의 중단

RCE VIA OOM CORRUPTION

PHP는 메모리 부족(OOM) 때 longjmp()로 현재 처리를 빠져나간다. 이때 초기화가 덜 된 요청 데이터가 남으면, 종료 정리 코드가 이를 정상 데이터로 취급해 메모리를 손상시킬 수 있다.

초기화 진행 중→OOM 중단→잘못된 정리

대표 입증: Apache mod_php에서는 앱 코드 실행 전 요청 시작 단계의 RCE가 검증됐다. FPM은 시작 실패 시 자식 워커를 종료해 이 경로가 다르다. 공식 OOM 권고는 FPM의 영향 가능성을 설명하지만 해당 경로의 완전한 FPM 공격 입증은 명시하지 않는다.[02]

CVE-2026-1096199.2 CRITICAL

이전 요청을 가리키는 상태

RCE VIA STALE GLOBAL STATE

요청 메모리를 해제해도 워커의 전역 상태가 옛 주소를 보관할 수 있다. 같은 워커의 다음 요청이 초기화 전에 이를 사용하면, 해제 후 사용(use-after-free)이 발생한다.

참조가 남음→메모리 해제→다음 요청이 사용

대표 조건: 상태를 남기는 동작(producer)과 다음 요청에서 이를 쓰는 동작(consumer)이 필요하다. 세션 수명주기 경로는 mod_php와 FPM에서 검증됐다. FPM 경로에는 정상 시작 후의 앱 동작과 fatal error 조건 등이 관여한다.[03]

‘해제 후 사용’을 책상에 비유하면

정상 정리
워커의 주소 메모→비움 · NULL

방을 비울 때 주소 메모도 함께 지운다. 다음 요청은 새 상태를 만든다.

오래된 참조가 남은 경우
워커의 옛 주소→해제 · 다른 용도로 재사용

방 주인은 바뀌었는데 옛 메모를 믿고 들어간다. 잘못된 데이터를 객체처럼 다룰 수 있다.

이해를 위한 비유다. 실제 성립 여부에는 메모리 재사용, 상태 종류, 오류 시점 등이 관여한다.[13]

OOM · 메모리 부족이란?

Out of Memory. 요청 처리에 필요한 메모리를 더 할당하지 못하는 상태다. PHP의 memory_limit 도달과 실제 시스템 할당 실패는 구별해야 한다.

워커 · 요청마다 새로 생길까?

웹 요청을 처리하는 프로세스다. 환경에 따라 같은 프로세스가 여러 요청을 연속 처리하므로, 요청 사이에 남은 상태가 중요하다.

RCE · 무엇을 실행한다는 뜻일까?

Remote Code Execution. 외부 입력을 통해 서버에서 의도하지 않은 코드를 실행시키는 것이다. 획득 권한은 프로세스의 실행 계정에 좌우된다.

공식 CVSS v4.0 벡터에는 사전 권한 불필요(PR:N), 사용자 동작 불필요(UI:N)와 함께 높은 공격 복잡도(AC:H), 추가 실행 조건(AT:P)이 명시된다. ‘비인증’은 ‘어떤 서버든 한 번에 성공’과 다르다.[02][03]

OUTCOME B / REMOTE CODE EXECUTION

서버 권한으로 데이터에 접근

RCE가 성공하면 공격자는 PHP 워커 계정이 읽을 수 있는 설정·파일과 연결 가능한 서비스에 접근할 수 있다. DB 자격증명이나 클라우드 권한이 과도하면 피해가 더 커질 수 있다.

자주 생기는 오해

긴급하게 대응하되, 확인된 사실과 해석을 구분한다.

08
PHP-FPM이면 안전한가?

안전하다고 볼 수 없다. mod_php와 FPM은 요청 시작 실패 때의 처리 방식이 다르지만, 다른 세션·앱 경로가 존재한다. 공식 개별 권고와 Foundation 회고는 FPM 입증 범위의 서술에도 차이가 있다. 이 리포트는 경로별 조건을 구분하고, FPM도 업데이트 대상으로 취급한다.[02][03][05]

WordPress만 최신으로 바꾸면 되는가?

PHP 런타임 업데이트가 필요하다. CMS 업데이트 화면과 호스팅의 PHP 관리 화면은 다를 수 있다. 공급자의 PHP 패키지나 컨테이너 이미지가 수정됐고, 실행 중인 서비스에 반영됐는지 확인한다.[10]

로그인·MFA가 있으면 공격을 막는가?

애플리케이션 로그인 이전에 도달할 수 있는 경로가 있다. 따라서 앱의 MFA만으로 런타임 결함이 해결되지는 않는다. 앞단의 네트워크 접근 통제는 도달 가능성을 줄일 수 있지만, PHP 업데이트는 별도로 해야 한다.[02]

공개된 PoC가 있다는 것은 대규모 침해가 확인됐다는 뜻인가?

그렇지 않다. PoC가 크래시만 보여 주는지, 특정 환경의 RCE까지 재현하는지, 실전에서 성공했는지 구분해야 한다. CrowdStrike는 공개 코드 다수가 크래시 검증 수준이며 안정적 RCE로 바꾸는 작업은 별도라고 설명했다.[13]

패치를 했으면 이미 빼앗긴 비밀번호도 안전해지는가?

패치는 이후의 취약 경로를 수정한다. 이미 탈취된 자격증명, 공격자가 만든 계정이나 지속성은 자동으로 제거하지 않는다. 침해가 확인되면 조사 범위에 따라 세션·토큰 폐기, 키·비밀번호 교체, 재배포를 수행해야 한다.[08][09]

“AI가 공격자보다 먼저 찾았다”는 설명은 어떻게 읽어야 하나?

OpenAI는 공개 당시 ‘자사가 아는 한’이라는 한정으로 이를 설명했다. 한편 AWS는 10/17 공격 시도를 보고했다. 연구팀의 여름 발견, 공개 전 공격 시도, 성공한 침해 여부는 서로 다른 사실이며, 비공개 기간 전체가 안전했다고 추론할 수 없다.[07][12]

RESEARCH TAKEAWAY

발견의 속도만큼, 수정이 현장에 도달하는 속도가 중요하다.

AI는 오랫동안 어려웠던 분석과 실험의 비용을 낮췄다. 동시에 패치·공개 정보에서 공격을 만드는 비용도 낮아질 수 있다. 운영자의 실질적인 방어 능력은 자산 목록, 신속한 런타임 교체, 적용 검증, 그리고 사고 조사 체계에 달려 있다. 이는 공개 연구와 대응 권고를 종합한 이 리포트의 해석이다.[07][12]
